Project overview

Chief-Sef aims to pre-screen malware by combining PE features, Shannon entropy and API usage. Explainable measurements and the final human decision are at the heart of the design.

Development process

5 October 2026 · Transparency note: I am not building Şef alone but together with AI. I work with Claude Code for coding, and I also get support from Claude in technical discussions and text drafts. I decide which features are added, how results are interpreted and what gets published; I try to test and verify every output the AI produces. AI is a powerful tool and the decision belongs to a human: the architect of the system is a human, but the tools that write the code are agentic AIs.

  1. Static feature extraction and a Random Forest model were built on real EMBER data.
  2. Measurement consistency was examined with temporal and independent tests; Phase 1 closed on 25 September 2026.
  3. Measurements showed that the model misses most recent .NET malware; an experimental .NET specialist model is in progress to address this.
  4. The native model moved to EMBER2024 (17 October 2026): both classes from EMBER2024 data, 86 features including string features, balanced training within each file type; the decision criteria were written down before any result was seen.
  5. Phase 2 (Linux system-call monitoring with eBPF) and Phase 3 (NPU/TEE hardware isolation) have not started yet; they are on the roadmap.

Feasibility and status

In my assessment, Şef is viable as a research and pre-screening layer, but it is not yet at the point of making a security decision on its own. For the Phase 1 model (EMBER 2018, 5 features) the README reports 83.8% temporal accuracy, 90.1% same-period accuracy and a 3.5% independent false-alarm rate.

That model has been replaced by the native model trained on EMBER2024. Thresholds were chosen on held-out training weeks 48–51, for 1% false alarms per file type; the test weeks 52–63 (959,738 files) were measured once with those fixed thresholds:

File typeMissed malwareFalse alarms on EMBER2024 benign files
EXE17.7%0.83%
DLL19.5%1.43%

Overall test AUC 0.9865. On 5,635 real benign files from this machine: false alarms 0.25% (EXE) and 0.21% (DLL). How to read these numbers:

  • 50% of the test files are malicious. EMBER2024 is sampled 50/50 per week. 0.83% is the share of EMBER2024's benign EXEs that raised an alarm, not the share of alarms that are false. In real use malware is far rarer, so the real probability behind a given score is lower and the share of alarms that are false is higher.
  • The DLL false-alarm rate exceeds its 1% target (1.43%). The threshold was set on weeks 48–51; a likely cause is drift over time, but that cause was not measured. The threshold has to be re-validated over time.
  • The local validation set is aging. Since it was measured on 9 October, 857 of its files have been deleted and hundreds updated; the 5,635 rows the measurements rely on are frozen instead of being re-scanned.
  • Random Forest beat LightGBM only against untuned LightGBM; a tuned LightGBM is a separate, not-yet-run experiment. The .NET specialist model is not yet connected to the prediction tool.

Source of the numbers: README, “Native model” section. The next step is a small, measurable eBPF experiment on Linux. I will consider the NPU/TEE side only once the threat model, the hardware choice and the latency cost are clear.

Research notes

  • My model scored 90%. On a temporal split, it scored 83.8%When training and test data come from the same month, the score gets artificially easy; the realistic number comes from a temporal split.
  • A 90%-accurate model missed 93% of recent .NET malwareAn overall score can hide a subgroup collapsing: the .NET blind spot and the “DLL means benign” shortcut.
